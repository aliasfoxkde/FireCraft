EXTENSIONS · IN DEVELOPMENT

Make room for your workflow.

FireCraft is planning an extension ecosystem for focused commands, panels, tools, and reusable resources. Today, there is no public extension catalog or one-click installer. This page explains what we intend to build and the safeguards it must meet first.

DESIGNED FOR TRUST

Know what you install.

Publisher, source, license, compatibility, permissions, and review status should be visible before an extension can be enabled.

Fetching and staging a package must never silently turn on its code.

BUILT AROUND REAL TASKS

Useful tools, close to the canvas.

TWO CLEAR SUPPORT TIERS

Know who stands behind it.

Community visibility does not imply FireCraft endorsement. Each tier needs its own ownership and support expectations.

MAINTAINER OWNED

Official

FireCraft maintainers own the compatibility promise, test releases against supported API versions, publish immutable releases, and handle support through the project.

  • Maintainer source and release history
  • Declared app/API compatibility
  • Explicit support owner
INDEPENDENT PUBLISHER

Community

Independent authors retain ownership and support. A listing should show the publisher, source, license, compatibility, permissions, and the precise checks completed.

  • No implied maintainer endorsement
  • Review labels name the actual checks
  • Promotion requires an explicit ownership transfer

A RELEASE GATE, NOT A BADGE

Safety before convenience.

A public catalog and in-app installation should launch only after the package and review systems can support them.

01

Provenance

Trace each immutable package to its source revision, publisher, license, and release record.

02

Compatibility

Validate the manifest and app/API range; publish exactly which automated and human checks ran.

03

Permission clarity

Show capabilities and data/network behavior before install and again before first enable. Ask again when permissions expand.

04

Recovery

Stage installs per user, retain prior versions, support rollback and safe startup, and provide a security-report path.

A one-click flow is a future goal, not a current capability. Downloading or staging must remain separate from explicitly enabling executable code.

COMMUNITY SUBMISSIONS · PLANNED

A place for creators to share tools.

When the package format, validation, publisher identity, moderation, security response, and rollback paths are ready, authors will be able to submit community extensions for review. Listings will show their publisher, source, license, compatibility, requested capabilities, and exactly which checks have run.

01

Submit

Provide a versioned package, source revision, manifest, license, changelog, compatibility range, and capability declaration.

02

Review

Automated package checks and human review have separate, visible status. A submission is not endorsed just because it is listed.

03

Publish

Approved community releases remain distinct from maintainer-owned official tools, with immutable versions and clear support ownership.

04

Promote

Authors may propose official adoption later. Promotion requires explicit rights, ownership, support, security, and release commitments.

Not open yet: this page does not accept extension packages or provide a live marketplace. Suggest an extension use case through the existing issue form.
