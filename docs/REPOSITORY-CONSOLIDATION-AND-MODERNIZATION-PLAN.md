## 1. Mission and intended outcome

Bring FireCraft from a rapidly evolving collection of parallel branches and partially completed product work into a coherent, maintainable, release-ready application with a clear product direction.

This program has five outcomes:

1. **One trustworthy source tree:** local work, open PRs, feature branches, release experiments, generated artifacts, and documentation are reconciled without losing unique work.
2. **A better architecture:** high-coupling application modules are separated along stable responsibilities while preserving the shared document model, command registry, journal, and cross-platform behavior.
3. **A polished product:** existing workflows are finished and validated before adding large new capability areas.
4. **Disciplined feature transfer:** the best ideas from Krita, Photopea, Pixlr, GIMP, Inkscape, Penpot, SVG-Edit, and other relevant tools are evaluated and implemented independently where appropriate. Compatible open-source code may be reused only after a file-level license and architecture review.
5. **Reliable delivery:** the editor, website, documentation, CI, release artifacts, and deployment procedures tell the same truth and can be independently verified.

This is not a directive to merge every branch, port entire applications, rewrite the GUI, add every feature in the benchmark, or change FireCraft's license. The agent must preserve working behavior, recover valuable work, reduce integration risk, and deliver evidence for every claim.

## 2. Operating principles and authority

### 2.1 Repository authority

Read AGENTS.md before any repository action. The mandatory rules include:

- Pure Rust core and the enforced workspace dependency layers.
- The fwpng crate remains standalone.
- Unsafe code is forbidden.
- Production code does not use unwrap, expect, panic, unreachable, todo, or unimplemented.
- Hostile file data and dimensions are bounded and return typed errors.
- No placeholders, duplicate implementations, or versioned source files such as foo_v2.rs.
- No Adobe source, code, artwork, proprietary binaries, or content from the local source/ installation may be committed.
- The root workspace and web crate must remain wasm-compatible.
- Existing generated parity, scorecard, corpus, and release evidence must be regenerated by their authoritative tools, not hand-edited.
- Changes to web/ or the shell require a real-browser verification.
- Follow the documented remotes and push order. The repository manual specifies GitForge first and GitHub origin second; use the currently configured remote names and credentials without guessing.

If this plan conflicts with AGENTS.md, AGENTS.md wins. If documentation conflicts with current source, tests, generated evidence, or a verified deployment receipt, investigate the discrepancy and reconcile the documentation in the same focused change.

### 2.2 Status vocabulary

Every feature, PR, platform, and deployment must use an evidence-backed state:

- **Verified implemented:** the behavior exists in the current source and its relevant automated tests pass.
- **Workflow verified:** the end-to-end user workflow was exercised at the actual intended surface.
- **Partial:** some behavior exists, but a defined acceptance criterion remains incomplete.
- **Local only:** useful work exists in a local checkout/worktree but is not represented on the intended remote branch.
- **In progress:** a named agent/owner actively owns the work and the scope is recorded.
- **Blocked:** the exact external dependency or technical blocker is identified.
- **Deferred:** intentionally postponed with an explicit reason.
- **Unverified:** evidence is unavailable or stale. Do not convert unknown into complete or missing.
- **Rejected:** evaluated and deliberately declined, with a reason.

A command registry entry, source file, screenshot, build recipe, PR, green compile, or generated feature list does not by itself prove a usable product workflow. A feature is user-visible only when the appropriate UI, automation, or export surface is verified.

### 2.3 One objective per integration unit

Each implementation PR should have one primary objective, explicit files/surfaces owned, focused regression tests, and a reproducible acceptance receipt. Avoid broad PRs that mix shell refactoring, deployment, docs, release tooling, and unrelated product features.

Prefer multiple reversible, independently reviewable PRs to one large merge train. Do not optimize for the smallest PR count; optimize for safe review and low-risk integration.

## 4. Phase 0 — Protect work and establish ownership

**Priority: P0. No feature implementation or destructive cleanup before this phase exits.**

### Objectives

- Identify the actual development checkout and all active worktrees.
- Preserve uncommitted, staged, untracked, ignored-but-relevant, and local-only work.
- Establish file-level ownership across all agents and worktrees.
- Refresh the remote PR/branch inventory and determine whether any snapshot above has changed.

### Required actions

1. Confirm repository root, current branch, HEAD SHA, configured remotes, upstream/tracking state, and active toolchain.
2. Collect a read-only snapshot from every known active checkout/worktree:
   - branch and HEAD SHA;
   - staged and unstaged changes;
   - untracked paths;
   - ignored build/cache paths that contain meaningful work;
   - worktree filesystem location;
   - owning agent/task and files currently being edited.
3. Inspect local branches, remote-tracking branches, tags, all open PRs, PR review comments, commit status/check-runs, and base/head ancestry.
4. Compare local-only commits with all remotes and tags. Identify unique commits before considering a reset, rebase, cherry-pick, squash, or deletion.
5. Ask active agents for a short ownership report. Do not infer that an idle-looking worktree is abandoned.
6. Capture a preservation inventory before changing any checkout. Store its report in an appropriate ignored local handoff path or in the new audit report if it contains no private paths/secrets.
7. Record exact blockers and ownership conflicts.

### Read-only commands

Run these only from the relevant checkout and adapt paths/remote names to the actual environment:

~~~bash
git status --short --branch
git rev-parse HEAD
git remote -v
git branch -vv
git worktree list --porcelain
git log --oneline --decorate --graph --all -80
git tag --list --sort=-creatordate | head -40
git status --ignored --short
~~~

For each branch under consideration, compare it with current main and inspect commits that are not present on any remote. Do not rely on ahead/behind counts alone; inspect unique patches and their file/test scope.

### Prohibited during Phase 0

- No git reset --hard.
- No git clean, including git clean -fdx.
- No force push or branch reset.
- No bulk worktree prune or branch deletion.
- No git stash as a shortcut for unidentified work.
- No broad git add -A in a checkout with generated files or another agent's changes.
- No shared implementation edits by competing agents until file ownership is established.

### Exit criteria

- Every local worktree and relevant local-only commit has an owner or a documented disposition.
- No uncommitted work is at risk of being discarded.
- Every open PR has a current head/base SHA and current check/review state.
- A current branch/PR/commit inventory exists.
- All file conflicts have a named integration owner and an order.

## 8. Phase 4 — Structural refactoring and code health

**Priority: P1. Refactor after integration, one boundary at a time. Refactoring must not change behavior.**

### 8.1 Establish the baseline first

Before each refactor:
1. Identify production code versus tests/static data.
2. Capture file/line metrics, public/private symbol inventory, module dependency graph, test inventory, and existing coverage.
3. Run focused unit, integration, UI, corpus, and browser tests for the affected surface.
4. Identify the module's real responsibility and its data ownership.
5. Write a short design note if the extraction changes visibility or the module graph.

Do not refactor based solely on line count. Preserve small diffs and prove behavior equivalence.

### 8.2 Priority refactor candidates

| Priority | Area | Why | Proposed direction |
|---|---|---|---|
| R1 | crates/app/src/shell/panels.rs | Roughly 4,600 production lines in the observed main snapshot; panel families and builders are concentrated | Split by responsibility into panel modules while preserving Shell command dispatch and read-only view semantics. |
| R2 | crates/app/src/shell/mod.rs | Large mixed shell implementation and a substantial nested test module | Extract tests first; then move cohesive responsibilities to existing/new sibling modules. |
| R3 | crates/app/src/editor.rs | Large Editor implementation combining tool/gesture domains | Split pointer/gesture, selection/transforms, vector interaction, bitmap interaction, text interaction, and viewport logic where boundaries are real. |
| R4 | xtask/src/dist.rs | Large build/release module | Separate native/web artifacts, manifest, SBOM/provenance, verification, and smoke orchestration. |
| R5 | crates/app/src/menus.rs | Large file but much is declarative menu data and tests | Separate tests and schema/data only if it improves ownership; do not mistake data volume for complex production logic. |
| R6 | crates/app/src/shell/panels_web.rs | Web-specific panel surface | Keep browser-only behavior isolated; reuse shared command and model interfaces, not duplicate panel business logic. |

These rankings are initial hypotheses. Re-measure on the exact main SHA after PR integration and update the ordering.

### 8.3 Panel module split

A candidate structure, subject to actual symbol ownership:

- panels/properties.rs
- panels/layers.rs
- panels/pages_states.rs
- panels/history.rs
- panels/styles_resources.rs
- panels/fill_stroke.rs
- panels/help.rs
- panels/shared.rs

The split must:
- Keep panel rendering read-only with respect to document state.

## 10. Phase 6 — Competitive feature adoption and code-reuse program

**Priority: P1 research, P2/P3 implementation unless it closes a proven current gap.**

### 10.1 The rule: learn broadly, reuse selectively

"Extract features" means identify the user problem and successful behavior, then build a FireCraft-native solution that fits the existing document model and engine. It does not mean copy another application's UI, artwork, assets, or code without permission.

Code reuse is allowed only when:
- the exact source repository, commit, file path, copyright notice, and SPDX/license text are recorded;
- all file-level and transitive licenses are compatible with the project's distribution model;
- dependency tree, native libraries, wasm support, security, MSRV, maintenance, compile-time, and binary-size costs are accepted;
- the code fits FireCraft's Rust/document/command architecture without a second application runtime;
- tests prove correctness and no source provenance is ambiguous;
- docs/ATTRIBUTION.md is updated in the same change;
- the project owner approves any copyleft, dual-license, trademark, or project-license change before integration.

The repository currently states Apache-2.0 as its source license. Maintaining that single-license posture is the default. Do not silently bring GPL code into the application, and do not assume a whole application shares the license of a permissively licensed file found inside it.

### 10.3 Feature-transfer workflow

For each candidate feature:
1. Write the user problem, not the competitor product name.
2. Record the best source references, observed workflow, version/date, and limitations.
3. Search current FireCraft source, task board, issues, branches, and PRs for existing work.
4. Mark the candidate as existing, polish, extend, new, defer, or reject.
5. Create a capability comparison: expected UX, engine support, document-model change, rendering cost, CLI/script/MCP behavior, platform support, and export semantics.
6. Complete a license/provenance review before any code reuse.
7. Write an ADR before document-format changes, plugin/service boundaries, or new persistent semantics.
8. Build a small proof-of-concept against the current architecture.
9. Add unit, property, corpus, UI, browser, and performance tests at the layer where the risk exists.
10. Ship one coherent user workflow, documentation, and a truthful feature status.

### 10.4 Feature clusters and priority

#### A. Professional brush and stylus workflows

- Pressure-aware brush size/opacity, spacing, hardness, angle, rotation, and smoothing.
- Tablet diagnostics displaying the actual pressure, tilt, barrel-button, eraser, and pointer events received.
- User-configurable pressure curves and device profiles.
- Brush preset library with search, categories, favorites, tags, previews, import/export, and missing-resource handling.
- Popup palette for commonly used colors, brushes, recent tools, canvas rotation/zoom/mirroring, and workspace actions.
- Tablet-oriented workspace with larger hit targets, collapsible panels, and explicit pen/touch behavior.

Prove native and web input independently. Do not claim stylus support based on mouse input or an API type existing in source.

#### B. Non-destructive editing and Smart Assets

Evaluate a distinct Smart Asset model:
- Embedded source content for portability.
- Optional linked sources with missing/relink state.
- Multiple independent instances referring to one source.
- Independent transforms for placed instances.
- Edit-source workflow with clear shared-instance semantics.
- Non-destructive adjustment/filter stacks with reorder, disable/enable, parameter edit, mask, and preview.
- Defined export behavior for unsupported or flattened features.

Do not conflate Smart Assets with design Components. Smart Assets model source content and non-destructive placement; Components model reusable design structures and behavior. This is a document-model and file-compatibility decision. Write an ADR and migration plan before adding persistent nodes/fields.

#### C. Quick Actions and guided workflows

Build discoverable actions over existing engine commands:
- Crop, resize, rotate, straighten, convert, and fit to target dimensions.
- Levels, curves, exposure/brightness/contrast, hue/saturation, and color balance.
- Heal, clone, blur, sharpen, denoise, and background isolation only when engine reliability is adequate.
- Export selected layer, selection, page, state, asset, or sprite with an explicit preset.

Every action must call the same engine/command path used elsewhere, support undo, preview or confirmation for destructive operations, cancel safely, and expose advanced controls for expert use. Do not create a second editor engine for quick actions.

#### D. Color management and print-quality workflows

- ICC profile awareness and explicit import/export conversion.
- Display rendering intent and black-point compensation.
- Soft proofing and out-of-gamut warnings.
- RGB/CMYK/Lab distinctions and export conversion warnings.
- Print dimensions, DPI, and bleed only after the color pipeline is defined.

Do not add a profile picker without a coherent color pipeline and test profiles. Complete the color-management ADR and dependency review first.

#### E. Vector and typography depth

- Bézier node ergonomics, path operations, snapping, guides, assistants, precision constraints.
- Better SVG import/export fidelity with a formal capability matrix.
- Text shaping, font discovery/management, variable-font behavior, and missing-font handling.
- SVG filter and mask semantics.
- Clear warnings when round-tripping external formats loses information.

Do not promise complete SVG/PSD/AI compatibility from a filename extension or a single sample file.

#### F. Resource and design-system management

- Unified searchable resource manager for brushes, swatches, gradients, styles, symbols, patterns, and reusable assets.
- Tags, favorites, dependency/usage graph, preview, import/export, missing-resource handling, and safe replace/delete.
- Named color palettes and semantic/design tokens.
- Component variants and shared design structures after a page/artboard/component ADR.

#### G. Animation and interactive design

- Preserve and polish the existing states/timeline/GIF workflow.
- Evaluate tweening, onion skin, preview controls, frame export, and sprite atlas.
- Prototype simple hotspots/transitions/interactions without making the core editor depend on a hosted collaboration service.
- Use existing slice/hotspot concepts and web export pipeline where possible.

#### H. AI-assisted operations

Later and optional:
- Subject/background segmentation, generative fill/expand, upscaling, layer extraction, and prompt-assisted edits.
- Local provider adapters and remote providers must be separate implementations.
- Require explicit user initiation, clear local-vs-remote disclosure, cost/provider disclosure, preview, cancellation, and failure recovery.
- Never upload document pixels by default.
- Core open/edit/save/export must work without AI or network access.

### 10.5 Rust/library reuse candidates

In addition to application references, evaluate small-purpose libraries rather than importing an entire GUI framework. Build a shortlist for vector tessellation, SVG parsing/rendering, raster formats, font shaping, image operations, color management, and geometry.

For each candidate verify:
- exact current crate license and third-party notice;
- dependency and native-code tree;
- wasm32 support and feature flags;
- compile time and final binary/WASM size;
- API stability and maintenance;
- fuzzing/security state;
- overlap with existing FireCraft modules;
- whether it replaces code or creates duplicate parallel logic.

Prefer pure-Rust and permissively licensed dependencies where technically sound. Avoid adding multiple overlapping image/geometry libraries. No library is approved merely because it is popular or has an attractive top-level SPDX badge.

### Exit criteria

- Every adopted idea has a defined user benefit and an existing-code gap check.
- Every reused line/library/asset has verified provenance and a compatible license decision.
- New document semantics have an ADR and migration/corpus coverage.
- Features are delivered through existing command/document/undo/export architecture.
- Browser/native behavior and performance are measured.
- Feature claims remain bounded by tested capabilities.

## 18. Stop conditions and escalation

Stop and report rather than guessing when:
- A local worktree contains unidentified or uncommitted owner/agent work.
- A branch or PR has changes not attributable to a current owner.
- A deletion could remove a unique commit, release tag, deployment record, or test fixture.
- Two PRs alter the same source/ledger and merge order is unresolved.
- An upstream license is absent, ambiguous, file-level, or incompatible with the intended distribution posture.
- A proposed copied code path is GPL/copyleft and no owner-approved license decision exists.
- A format/document-model change would discard unknown data or lacks a migration plan.
- A production deploy would change project settings, domain, DNS, or output path without owner authorization.
- CI results are skipped, stale, cancelled, or from a different SHA.
- A feature cannot be validated on its intended surface or the required hardware/device is unavailable.
- An AI/cloud operation would transmit user artwork without explicit consent and clear disclosure.
- A test failure is being hidden by weakening a gate or changing a golden/coverage/parity floor without evidence.

Escalation reports must include: exact SHA, command/URL, evidence, impact, attempted safe options, and the one decision needed from the owner.
